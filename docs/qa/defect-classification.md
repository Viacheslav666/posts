# Классификация дефектов Posts

| | |
|---|---|
| Версия | 1.0 |
| Задача | QA-1 |
| Связано | [test-strategy.md](test-strategy.md), [шаблон баг-репорта](templates/bug-report.md) |

Severity отвечает на вопрос «насколько больно продукту/данным», priority — «когда чинить». Severity выставляет QA при заведении; priority согласуется с владельцем/тимлидом зоны (может отличаться от severity при бизнес-ограничениях).

## 1. Severity (серьёзность)

| Уровень | Определение | Примеры для Posts | SLA реакции (staging/prod) |
|---|---|---|---|
| **Blocker** | Полный стоп ключевого сценария **или** нарушение главного обещания: потеря/дубль публикации, утечка данных/токенов, невозможность входа или оплаты | Пост исчез из очереди; два одинаковых поста в TG; токены VK в логах API; нельзя зарегистрироваться/оплатить; массовый IDOR чужого workspace | Немедленно; стоп релиза / hotfix |
| **Critical** | Критичный путь сильно сломан без приемлемого обхода; риск массовых сбоев или нарушения закона/SLO | Конвейер не публикует одну сеть; 2FA обходится; биллинг списывает дважды при повторном вебхуке; p99 стабильно > 60 с на staging в L2 | ≤ 4 ч в рабочее время; блокер релиза MVP |
| **Major** | Существенная функция работает неверно; есть обходной путь | Неверный предпросмотр Max; drag&drop календаря сбрасывает TZ в краевых случаях; уведомление об ошибке только in-app без email | ≤ 2 раб. дня; на релизе MVP — только с согласием владельца и обходом (лимит ≤ 5 открытых) |
| **Minor** | Локальный дефект UX/копирайта/некритичной валидации | Неточный текст ошибки 402; лишний скролл в модалке приглашения | Очередь бэклога |
| **Trivial** | Косметика, опечатки, мелочи без влияния на сценарий | Опечатка в подсказке; выравнивание иконки сети | По возможности / вместе с соседними правками |

### Правила эскалации для конвейера публикаций

Любой подтверждённый случай **потери** или **дубля** публикации (TC-PUB / L2 / хаос / прод-синтетика) = **Blocker**, независимо от частоты «пока один раз».

Подозрение без воспроизведения: завести баг как Critical/Major с меткой `needs-repro`, приложить `trace_id` / логи / id публикации; после подтверждения — переклассифицировать.

## 2. Priority (приоритет исправления)

| Уровень | Когда ставить | Типичная связка со severity |
|---|---|---|
| **P0** | Чинить сейчас: блокер релиза, прод-инцидент, потеря/дубль, безопасность данных | Blocker, большинство Critical |
| **P1** | В текущем спринте / до ближайшего релиза | Critical, Major без обхода |
| **P2** | Планово в бэклоге | Major с обходом, Minor |
| **P3** | Когда-нибудь / при касании файла | Trivial, часть Minor |

Метки GitHub: `P0`, `P1`, `P2` (и при необходимости `P3`); плюс `role:qa` / зона (`backend`, `frontend`, …), `phase:0|1|2|3`.

## 3. Матрица «severity → рекомендуемый priority»

| Severity ↓ / Impact → | Прод / релизный гейт | Staging до релиза | Только local / flaky тест |
|---|---|---|---|
| Blocker | P0 | P0 | P0 (чинить тест/код) |
| Critical | P0 | P0–P1 | P1 |
| Major | P1 (или P0 если нет обхода) | P1–P2 | P2 |
| Minor | P2 | P2 | P2–P3 |
| Trivial | P3 | P3 | P3 |

## 4. Связь с критериями выхода

- **Релиз MVP:** 0 открытых Blocker/Critical; ≤ 5 Major с обходным путём и **явным согласием владельца**.
- **Выход из story:** 0 Blocker/Critical по story; Major — исправлены или приняты с обходом.
- Дефекты безопасности с подтверждённой эксплуатацией данных пользователей = минимум Critical (часто Blocker).

## 5. Оформление

Обязательные поля — см. [templates/bug-report.md](templates/bug-report.md): окружение, шаги, ожидаемое/фактическое, severity, priority, `trace_id`/логи, артефакты Playwright, затронутые TC-ID и story.
