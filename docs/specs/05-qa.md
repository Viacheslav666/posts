# 05. ТЗ для агента «Posts Тестировщик» (QA, автотесты, нагрузка, надёжность)

Прочитать: `00-overview.md`, `01-analyst.md` (stories и AC), `02-backend.md` (конвейер, API), `04-devops.md` (окружения, SLO), `agent-tasks.md`. Код: `tests/` (e2e Playwright, k6, эмулятор соцсетей, хаос), тесты бэка рядом с кодом в `backend/**/src/test` и `src/integrationTest`, документы: `docs/qa/`. Бэкенд — Java 21 / Spring Boot 3, фронтенд — Next.js.

## 1. Цели качества
- 0 потерянных и 0 задублированных публикаций (главный риск продукта).
- Публикация p99 ≤ 60 с от запланированного времени при пике 2 000 публикаций/с.
- Регрессия ключевых путей автоматизирована и проходит на каждом PR/merge.
- Нет критических уязвимостей OWASP Top 10 / API Top 10 на релизе.

## 2. Тест-стратегия (пирамида)
| Уровень | Кто пишет | Инструменты | Где запускается |
|---|---|---|---|
| Unit (домен, валидация лимитов сетей, рендер форматирования, повторы, биллинг) | Бэк/Фронт, QA ревьюит покрытие | бэк: **JUnit 5** + AssertJ + Mockito, JaCoCo; фронт: Vitest + Testing Library | каждый PR |
| Интеграционные (репозитории, Flyway-миграции, RabbitMQ, scheduler/publisher, Redis-лимиты) | Бэк + QA | JUnit 5 + **Testcontainers** (`@ServiceConnection`: Postgres, Redis, RabbitMQ, MinIO), Awaitility, Spring Boot Test | каждый PR (`./gradlew integrationTest`) |
| Контрактные API (OpenAPI ↔ реализация) | QA | **Schemathesis** (property-based по `docs/api/openapi.yaml`, сгенерированному springdoc) против поднятого posts-api, oasdiff | каждый PR / ночью |
| Контрактные адаптеров соцсетей (записанные ответы VK/TG/OK/Max, включая ошибки и таймауты) | Бэк + QA | **WireMock** (JUnit 5 extension), JSON-фикстуры | каждый PR |
| Архитектурные правила (границы модулей) | Бэк, QA контролирует | ArchUnit | каждый PR |
| Эталонные фикстуры форматирования (`docs/api/fixtures/formatting`) | QA ведёт набор кейсов | JUnit (бэк-рендер) + Vitest (фронт-предпросмотр) | каждый PR |
| E2E UI | QA | **Playwright** (Chromium, WebKit, мобильный viewport), MSW-заглушка соцсетей или sandbox-каналы | merge в main + ночью |
| Smoke на staging/prod против **реальных тестовых каналов** (VK-группа, TG-канал, OK-группа, Max-канал) | QA | Playwright + API-скрипты | после деплоя + каждые 30 мин (синтетика) |
| Нагрузочные | QA + Devops | **k6** (k6-operator в K8s), эмулятор соцсетей | перед релизом, еженедельно ночью на staging |
| Хаос/отказоустойчивость | QA + Devops | Chaos Mesh / ручные сценарии | перед релизом, ежеквартально |
| Безопасность | QA | OWASP ZAP (baseline в CI), ручные проверки IDOR/RBAC, Trivy/CodeQL (от Devops) | CI + перед релизом |
| Доступность и производительность фронта | QA + Фронт | axe-core в Playwright, Lighthouse CI | merge в main |

**Эмулятор соцсетей (`tests/social-emulator`)** — обязателен: HTTP-сервис (рекомендуется отдельное лёгкое Spring Boot-приложение или WireMock standalone с расширениями, Docker-образ для docker-compose и staging), имитирующий VK API, Telegram Bot API, OK, Max: настраиваемые задержки, ошибки (5xx, 429 с retry_after, VK error 6/9/10/15/100, таймауты без ответа, «успех, но ответ потерян»), учёт созданных постов для проверки дублей. Используется в e2e, нагрузке и хаос-тестах. Делается совместно с Бэком в спринте 1–2.

## 4. Критерии входа/выхода
- **Вход в тестирование story:** AC согласованы, задеплоено на staging, unit/интеграционные зелёные.
- **Выход (релиз MVP):** 100 % P0-кейсов пройдено, 0 открытых Blocker/Critical, ≤ 5 Major с обходным путём и согласием владельца; нагрузка и хаос по §6–7 пройдены; restore из бэкапа проверен; a11y без критичных нарушений.
- Классификация дефектов: Blocker (потеря/дубль публикации, утечка данных, невозможность оплаты/входа), Critical, Major, Minor, Trivial. Шаблон бага: окружение, шаги, ожидаемое/фактическое, логи/trace_id, скриншот/видео Playwright.

## 5. Ключевые тест-кейсы MVP (минимальный набор, расширить)
### Аутентификация и доступ
- TC-AUTH-01 Регистрация email → подтверждение → вход. TC-AUTH-02 Повторная регистрация того же email — ответ без энумерации. TC-AUTH-03 Брутфорс: 6-я попытка за минуту → 429/CAPTCHA. TC-AUTH-04 2FA: вход без кода невозможен; резервный код одноразовый. TC-AUTH-05 Refresh-токен reuse → отзыв всех сессий семейства. TC-AUTH-06 Смена пароля завершает другие сессии. TC-AUTH-07 VK ID/Яндекс ID вход и привязка к существующему аккаунту только с подтверждением.
- **RBAC/IDOR:** TC-RBAC-01…N — для каждой роли × каждого эндпоинта матрица разрешено/запрещено (автоматическая генерация из `roles-permissions.md`); TC-IDOR-01 доступ к посту/каналу/медиа чужого workspace по ID → 404; Author не может запланировать без согласования; Viewer не видит чужие проекты.

### Каналы
- TC-CH-01 Подключение VK-группы (админ) — успех; TC-CH-02 пользователь не админ — понятная ошибка. TC-CH-03 Telegram: бот без права публикации → ошибка с инструкцией; с правами → канал активен. TC-CH-04 Отзыв токена в сети → статус «переподключить» ≤ 5 мин + уведомление; посты канала не удалены. TC-CH-05 Превышение лимита каналов тарифа → 402 и предложение апгрейда.

### Редактор и посты
- TC-POST-01 Пост в 4 сети одновременно с вариантами — в каждой сети опубликован свой вариант. TC-POST-02 Превышение лимита символов/медиа для сети блокирует сохранение и подсвечивает поле. TC-POST-03 Форматирование TG/Max корректно конвертируется (таблица входов/выходов, включая вложенные теги, спецсимволы `<>&`, эмодзи, ссылки). TC-POST-04 Автосохранение и восстановление после закрытия вкладки. TC-POST-05 Конфликт версий при одновременном редактировании двумя пользователями → 409 и диалог. TC-POST-06 Таймзоны: пользователь UTC+4 планирует на 10:00 → публикация в 06:00 UTC; переход на другую TZ в настройках не сдвигает уже запланированное абсолютное время; граничные даты (конец месяца, 29 февраля, повтор «каждый месяц 31-го»). TC-POST-07 Повтор «будни 09:00» — материализация на 14 дней, пауза/возобновление серии, редактирование «только это / все последующие». TC-POST-08 Закреп + открепление в срок; автоудаление через N часов; удаление уже удалённого вручную поста не даёт ошибки. TC-POST-09 Первый комментарий появляется после публикации. TC-POST-10 Drag&drop в календаре меняет время; опубликованный пост перетащить нельзя. TC-POST-11 Bulk-пауза 500 постов — все `paused`, ни один не опубликован. TC-POST-12 Загрузка видео 1 ГБ с обрывом сети → резюмирование.

### Конвейер публикаций (самое важное)
- TC-PUB-01 Публикация в срок: 1 000 постов на одну минуту → все опубликованы, p99 задержки ≤ 60 с.
- TC-PUB-02 Эмулятор возвращает 5xx 3 раза → успех с 4-й попытки, ровно 1 пост в сети, 4 записи в `publication_attempts`.
- TC-PUB-03 Таймаут «успех, но ответ потерян» → повтор не создаёт дубль (findExisting/guid).
- TC-PUB-04 429/flood control с retry_after → ожидание не меньше retry_after, остальные каналы этой сети не блокируются сверх лимита.
- TC-PUB-05 Постоянная ошибка (нет прав) → `failed_permanent`, уведомление, без бесконечных ретраев.
- TC-PUB-06 Повторная доставка сообщения из RabbitMQ (одна задача дважды) → один пост.
- TC-PUB-07 Убийство пода `publisher-<network>` посреди публикации → задача доработана другим подом, дублей нет.
- TC-PUB-08 Рестарт scheduler / два scheduler одновременно → нет двойной диспетчеризации.
- TC-PUB-09 Недоступность RabbitMQ 5 мин → после восстановления все просроченные публикации выпущены (с отметкой задержки), ни одна не потеряна; пользователь уведомлён о задержке > 5 мин.
- TC-PUB-10 Failover PostgreSQL во время пика → потери 0, дублей 0, задержка восстановления фиксируется.
- TC-PUB-11 Изоляция сетей: VK-эмулятор «лежит» 30 мин → публикации в TG идут по SLA.
- TC-PUB-12 Пост отредактирован за 10 с до публикации → публикуется новая версия; пауза за 1 с до публикации → не публикуется (или публикуется, если уже `in_progress` — фиксируем ожидаемое поведение в AC).
- TC-PUB-13 Статусы в UI обновляются по WS ≤ 3 с после публикации.

### Биллинг
- TC-BILL-01 Триал 7 дней → по окончании без оплаты grace 3 дня → заморозка: посты `paused`, не удалены; после оплаты — разморозка и выбор, что делать с просроченными. TC-BILL-02 Вебхук ЮKassa дважды → одно начисление. TC-BILL-03 Подделанный вебхук (неверная подпись/IP) → отклонён. TC-BILL-04 Автопродление: отказ карты → 3 попытки по графику, уведомления. TC-BILL-05 Промокод: срок, лимит активаций, повторная активация тем же workspace запрещена. TC-BILL-06 Даунгрейд с превышением лимитов каналов → понятное поведение по AC (лишние каналы деактивируются по выбору пользователя). TC-BILL-07 Чек 54-ФЗ отправлен на email (sandbox ЮKassa).

### Уведомления
- TC-NOTIF-01 Ошибка публикации → email + TG + in-app ≤ 1 мин, с учётом настроек пользователя; TC-NOTIF-02 отписка от типа работает.

## 6. Нагрузочное тестирование (k6 + эмулятор соцсетей, staging с прод-подобными ресурсами)
| Сценарий | Профиль | Критерии прохождения |
|---|---|---|
| L1 API смешанный | 10 000 VU, 5 000 RPS: 60 % чтение календаря/списков, 20 % создание/редактирование постов, 10 % медиа-presign, 10 % прочее; 30 мин | p95 чтение ≤ 300 мс, запись ≤ 500 мс, ошибки < 0.1 % |
| L2 Пик публикаций | 1 500 000 каналов в БД, 120 000 публикаций, запланированных на одну минуту (2 000/с), повтор 3 «ровных часа» подряд | p99 задержки ≤ 60 с, 0 потерь, 0 дублей (сверка эмулятора с БД), очередь рассасывается ≤ 2 мин |
| L3 Выносливость (soak) | 30 % от пика, 8 часов | нет утечек памяти, стабильная латентность, рост БД предсказуем |
| L4 Stress / точка отказа | рост до ×2 пика | система деградирует контролируемо (очереди растут, API отвечает 429/503, не падает), восстановление без ручных действий |
| L5 Вебхуки ingest | 5 000 событий/с от эмулятора VK Callback/TG | ответ хендлера ≤ 100 мс p99, без потерь |
| L6 Объём данных | БД с 300 000 пользователей, 50 млн publications | запросы календаря ≤ 300 мс p95 (проверка индексов/партиций) |
Отчёт: графики Grafana, выводы, узкие места, тикеты на оптимизацию. Повторять перед каждым мажорным релизом и после изменений конвейера.

## 7. Хаос- и DR-сценарии (совместно с Devops)
Убийство случайных подов publisher/scheduler/api в пике; отказ узла K8s и целой зоны; failover PG; перезапуск RabbitMQ-узла (quorum сохраняет сообщения); недоступность Redis rate-limit (поведение: консервативный локальный лимит, без шторма запросов к соцсетям); сетевые задержки 500 мс к соцсети; полное восстановление БД из PITR на точку «5 мин назад» и сверка: сколько публикаций потребовали повторной обработки и не было ли дублей.

## 8. Безопасность (чеклист перед релизом)
OWASP ZAP baseline + активное сканирование staging; IDOR/RBAC-матрица; JWT (alg none, подмена, истёкшие); CSRF на cookie-эндпоинтах; XSS в тексте поста/предпросмотре/комментариях/именах каналов; SSRF в URL-полях (RSS, картинка по ссылке); загрузка файлов (polyglot, SVG со скриптом, zip-бомба, огромные размеры); rate limits; утечки токенов в логах/ответах API (поиск по логам staging); заголовки безопасности; проверка, что токены соцсетей в БД зашифрованы.

## 9. Процесс
- QA участвует в груминге: каждая story получает тест-кейсы до начала разработки (shift-left).
- Автотесты пишутся в том же спринте, что и фича; flaky-тесты — карантин с тикетом, исправление ≤ 1 спринт.
- Ежедневный ночной прогон полного e2e + синтетика на staging, отчёт в Telegram-канал команды.
- Регресс перед релизом: автоматический полный + ручной исследовательский (exploratory) 2 часа по чартерам (редактор, календарь, биллинг, мобильный вид).
- Метрики качества: escaped defects/релиз, покрытие P0 кейсов автотестами (цель ≥ 90 %), время прогона CI, доля flaky < 2 %.
