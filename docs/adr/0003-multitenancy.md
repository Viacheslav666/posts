# ADR-0003: Мультиарендность (workspaces)

- Статус: accepted
- Дата: 2026-11-17
- Авторы: Posts Разраб Бэк (BE-1)

## Контекст

Posts - multi-tenant платформа: агентства и бизнесы работают в изолированных рабочих пространствах с ролями, проектами и каналами. При 300 000 пользователей и до ~1.5 млн каналов нужна простая, проверяемая изоляция данных без потери производительности горячих запросов публикационного конвейера. Требования: `02-backend.md` §4, §8; командная модель из `docs/analysis.md` §8.2.

## Решение

1. **Граница арендатора - `workspace`.** Все доменные таблицы содержат `workspace_id` (UUID) и индекс по нему. Пользователь (`users`) глобален; членство - `workspace_members(workspace_id, user_id, role)`.
2. **Изоляция в приложении (обязательно):** каждый запрос к доменным данным фильтруется по `workspace_id` текущего контекста (из JWT / membership). Guard в репозиториях/сервисах; тесты на IDOR обязательны. Hibernate `@Filter` / Spring Data по `workspace_id` - основной механизм MVP.
3. **PostgreSQL RLS (опционально, hardening):** политики `USING (workspace_id = current_setting('app.workspace_id')::uuid)` можно включить позже как defense-in-depth; не блокер MVP. Hot-path диспетчера (`SKIP LOCKED` по `publications`) работает по глобальному индексу `(state, run_at)` и **не** обязан фильтровать по workspace - публикации выбираются кросс-тенантно по due-time; изоляция обеспечивается тем, что publisher оперирует только `publicationId` и связанными строками той же записи.
4. **Проекты** - группировка внутри workspace (`projects.workspace_id`); каналы и посты всегда несут и `workspace_id`, и опциональный `project_id`.
5. **Биллинг и лимиты** - на уровне workspace (`subscriptions`, `usage_counters`, `PlanLimitService`).
6. **Кэш/ключи Redis** - префикс с `workspace_id` там, где данные арендатор-специфичны; rate-limit ключи соцсетей - по сети/токену/чату (не по workspace).

## Альтернативы

- **Схема-на-арендатора / БД-на-арендатора** - отвергнуто: операционная сложность при сотнях тысяч workspace, миграции, connection storms.
- **Только RLS без application guard** - отвергнуто: легко забыть `SET app.workspace_id`; IDOR-тесты на уровне сервиса надёжнее как primary control.
- **Арендатор = user** (как у Впостера) - отвергнуто: блокирует командную работу и агентский сценарий.

## Последствия

- Все новые таблицы домена обязаны иметь `workspace_id` (кроме глобальных справочников вроде `plans`).
- Публикационный диспетчер остаётся глобальным по due-слоту; tenant-изоляция API не распространяется на внутренний poller.
- Аудит и метрики включают `workspace_id` в MDC.
- Фаза 2 (white-label, клиентский портал) строится на той же модели workspace/project без смены схемы аренды.
